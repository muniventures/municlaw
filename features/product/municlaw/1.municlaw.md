# Feature: MuniClaw cloud coding workspaces

Scope: Private cloud coding product with a separate web console, organization-dedicated Minicloud-managed VPSes, GitHub/GitLab repositories, BYOK model access, and OpenCode as the initial harness.

## Goal

A user connects a repository and their model API key, assigns a coding task, closes their browser, and returns to review changes, test evidence, and a pull request or merge request. Follow-up instructions continue the same task. Minicloud provisions and manages the coding infrastructure.

MuniClaw is a working product name. `ai.muni.dev` is the proposed console hostname; it is not provisioned by this specification. The product has its own frontend, navigation, onboarding, and deployment. It is not a page inside `cloud.muni.dev`.

## Current patterns learned

- Minicloud architecture documents describe a .NET control-plane API, React/shadcn dashboard, Firebase identity, organization-scoped data, and PostgreSQL-backed worker scheduling.
- The deployment worker owns provisioning and deployment lifecycle. The runtime telemetry agent reports logs/status; it is not a general coding executor.
- OpenBao stores managed secret values while the database stores references and metadata.
- Existing deployment and branch-domain contracts provide a possible later preview integration. They must not automatically copy production secrets into coding environments.
- These are integration foundations, not evidence that MuniClaw already exists. Shared-module extraction and other active work must be verified before implementation reuses them.

## Scope and non-goals

### In scope

- Private, allowlisted MVP with authenticated accounts and organization ownership from the beginning. The MVP admits one user membership per organization, but users, organizations, memberships, roles, actors, and ownership are modeled for multiple users from the start.
- One dedicated Minicloud-managed coding VPS per organization; multiple repositories and saved tasks on that VPS.
- GitHub.com and GitLab.com repository connections, private repository access, branches, and PR/MR delivery.
- User-supplied API keys for OpenAI, Anthropic, and DeepSeek through the supported OpenCode provider integrations.
- Responsive web console, streamed activity, durable conversation history, diffs, test results, permission requests, cancellation, and follow-up turns.
- One executing task per organization initially; other tasks queue. A task waiting for approval retains the execution slot in the MVP.
- Task limits, credential rotation/revocation, worker restart recovery, and inspectable failures.

### Out of scope

- Public signup, subscriptions, payment collection, and model-usage resale.
- Messaging integrations, native mobile applications, and scheduled autonomous work.
- User-owned VPS onboarding, shared customer VPSes, Kubernetes, and local model hosting.
- Multiple harness implementations or autonomous multi-agent teams.
- Self-managed GitLab instances and arbitrary user-defined provider endpoints in the initial release.
- Automatic merges, production deployments, or production-secret access.
- Preview deployment is a follow-on integration, not an MVP completion gate.

## Requirements

### User experience

1. An allowlisted user signs in to the separate console, selects their organization, and explicitly requests its coding workspace. Provisioning is an asynchronous onboarding action; sign-in alone does not create infrastructure.
2. An organization administrator connects GitHub and/or GitLab, selects repositories, and adds a provider key. Key values are write-only after submission.
3. The user creates a task with repository, base branch, instruction, provider/model, and limits. The UI discloses that selected code/context is sent to that model provider.
4. The worker prepares an isolated checkout and a dedicated task branch, then starts an OpenCode session.
5. The console shows persisted task state, streamed messages/tool activity, pending approvals, changed files, and actual test evidence. Browser delivery uses server-sent events with cursor replay. Browser disconnection does not cancel execution.
6. On completion, the user reviews the diff and requests publication to a task branch and draft PR/MR. Publication is a distinct authorized action and may run project CI.
7. A follow-up creates another run on the same task branch/session. Reopening an existing draft PR/MR updates it rather than creating duplicates.
8. Cancellation stops the active run and its child processes. Existing changes remain available. Resume is an explicit new run following reconciliation, not an assumption that a killed process continues.

Navigation: Tasks, Projects, Connections, Workspace, and Settings. Task detail contains conversation/activity, changes, checks, and delivery. Compact mobile layouts must support creating tasks, answering approvals, reading results, and cancelling work.

### Product and service boundaries

Repository placement (independent MuniClaw repository):

- `modules/ui/dashboard`: independently deployed React/shadcn frontend at `ai.muni.dev`.
- `modules/core`: domain, application services, persistence/migrations, and integration contracts.
- `modules/api`: MuniClaw application API with its own task domain and service identity; browser API served under the console's same-origin `/api` route.
- `modules/worker`: trusted VPS supervisor with an outbound authenticated connection to the MuniClaw API.
- OpenCode: pinned headless process inside the task sandbox, reachable only by the supervisor.

MuniClaw is authoritative for its organizations and memberships. It maps authenticated user identities to MuniClaw users and creates the scoped Minicloud service identity or ownership linkage required to manage infrastructure for each MuniClaw organization. Provisioning and secret-management integration uses versioned authenticated APIs. MuniClaw owns its own database and migrations; no sibling-repository project references or private-source dependencies. The worker accesses MuniClaw through scoped APIs, not database credentials. Do not share arbitrary database writes between products or give coding processes Minicloud administrative credentials. A separate console does not require users to create a second login identity.

MuniClaw owns tasks, runs, harness mappings, events, approvals, Git connections, delivery records, and usage records. Minicloud owns provider infrastructure and deployment lifecycle. Infrastructure linkage records carry both organization and managed-server identity. The proposed module/API split is not an implemented architecture change.

### Harness contract

OpenCode is the initial implementation of a small adapter: create session, submit prompt, subscribe to events, obtain session status/messages/diff, respond to approval, and abort. Preserve provider/model and harness version on every run.

OpenCode's documented HTTP server supports sessions, asynchronous prompts, events, permission replies, and cancellation. Exact version behavior, license obligations, reconnection semantics, and recovery must be qualified at T00 before implementation depends on them.

MuniClaw task/run IDs remain canonical. Persist the corresponding worker, workspace, and OpenCode session IDs. Do not expose the OpenCode server as the public product API. Unsupported operations must be reported explicitly rather than simulated as successful.

### Runtime and isolation

- Minicloud provisions a dedicated coding VPS, separate from production application VPSes, only after the user explicitly requests workspace creation during onboarding. Provisioning is asynchronous and exposes pending, ready, failed, and retryable states. The supervisor uses one-time registration and scoped, revocable runtime credentials.
- Each task has its own worktree, execution sandbox, home directory, and harness state. Persistent repository caches must not expose credentials or another task's writable files.
- Run unprivileged with CPU, memory, process, disk, and wall-clock limits; no privileged containers, host Docker socket, host credential mounts, or production network access.
- Docker-dependent tests require a separately qualified isolated builder; host Docker access is not an MVP shortcut. Show unsupported environment requirements clearly.
- Restrict network access to required source/model/package endpoints; block infrastructure metadata and private management networks. Repository code/configuration is untrusted and cannot broaden platform permissions.
- Keep OpenCode on loopback/private sandbox networking with authentication. The supervisor is outside the coding sandbox and exposes no arbitrary host-command endpoint.
- Setup commands are versioned Project configuration managed by MuniClaw. Repository content may suggest commands but cannot activate or modify them. A user confirms each configuration version before its first execution. Setup uses the same sandbox limits and trust boundary as coding.
- Preserve worktrees and harness state across process restarts. Persist user-visible events centrally. VPS/disk loss must produce a recoverable failure with clear data-loss reporting; transparent restoration of unpushed files is not promised in the MVP.
- Retain a task worktree for seven days after its latest terminal run by default, show expiry, and support earlier explicit deletion. A follow-up resets retention from its new terminal run. After deletion, a published task can be reconstructed from its published task branch in a new worktree and OpenCode session; conversation history remains visible, but harness-session continuation is not promised. Unpublished deleted work is not recoverable. Never silently delete an active task to reclaim space; reject admission when storage is insufficient.

### Lifecycle, delivery, and recovery

A Task is the durable conversation and branch container. Its lifecycle is `open -> archived`; it can contain multiple immutable runs. TaskRun owns execution state: `queued -> preparing -> running -> awaiting_input | completed | failed | cancelling`; approval returns the run to `running`, and `cancelling -> cancelled`. Preparation may fail or be cancelled. Each follow-up or resume creates a new TaskRun; terminal runs never silently restart.

Worker connectivity is separate from task and run state. Workers claim work through outbound authenticated HTTP long-polling. Claims carry a lease and fencing token; periodic heartbeats renew ownership and return commands after a command cursor. Events and results use bounded idempotent batches with acknowledgements. A lost heartbeat marks execution unknown/offline, not completed or safe to retry. On lost lease the worker stops new tool/model actions and terminates execution within a bounded grace period. Reconciliation must prove the old execution stopped before a replacement starts.

Use request idempotency keys, transactional queue claims, and per-organization execution exclusion. Persist events with monotonic per-run sequence numbers and replay cursors; duplicate transport delivery must not duplicate displayed activity or user actions. Never claim exactly-once model execution.

Track PR/MR publication separately from coding completion. Bind publication approval to the immutable repository identity, base commit, target branch, and reviewed commit. Persist those values and the remote PR/MR identity. Reconcile uncertain Git API outcomes before retries. If the remote task branch moved, stop and require reconciliation; never overwrite, automatically rebase, force-push, merge, or mutate the base branch. Git attribution is provider-specific: GitHub App installation identity is acceptable, while GitLab publication may use the connected OAuth identity.

### Data and validation

Organization-scoped entities: User, Organization, OrganizationMembership, CodingWorkspace, RepositoryConnection, Project, ProviderCredentialReference, Task, TaskRun, TaskEvent, ApprovalPolicy, ApprovalRequest, Delivery, and UsageRecord. The MVP enforces at most one active membership per organization as policy, not as a single-user schema shape.

- Every API read, event stream, worker message, secret lookup, and external side effect validates organization ownership server-side.
- Bind repository connections to the authenticated Git account/installation and immutable repository ID, not a user-provided URL alone.
- Record requested model/provider, resolved model, base commit, task branch, harness version, limits, actor, and timestamps.
- Store reported token usage and estimated provider charges with price provenance. Unknown usage/cost stays unknown; provider billing remains authoritative.
- Set finite request-output, run-duration, and tool-step limits. Estimated monetary budgets stop further requests when reached but are not exact provider billing caps; in-flight requests can finish and incur charges.
- Retain task history/events for 30 days by default, with bounded event payloads and explicit truncation indicators. Audit retention and infrastructure deletion are separate policies.

### Credentials and permissions

- Use GitHub App installation access and GitLab OAuth with validated state and supported PKCE/token rotation. T10 must verify current required scopes and revocation behavior.
- Store provider and Git credentials in scoped OpenBao paths. Provider credential metadata records its organization, owning user, creator, and a scope that can represent `personal` or `organization`; the MVP only permits `personal`. Organization-scoped sharing is deferred. Never include raw values in conversation, logs, database event payloads, or browser responses.
- Prefer a trusted credential/model proxy so repository-controlled shell commands never receive long-lived provider keys. T00 must prove compatibility with the selected providers; unsupported proxy behavior is a gate, not permission to expose keys silently.
- Git read/write operations use narrowly scoped trusted helpers. The sandbox cannot choose arbitrary repositories or retain reusable Git write credentials.
- Platform policy is enforced outside repository-controlled configuration. Harness permission prompts are not the sandbox security boundary.
- Organization administrators manage connections, keys, policy, and workspace lifecycle. Members may run tasks and approve their own task actions within organization policy; membership is checked again when applying approvals. The one-member MVP must use the same membership and actor checks required by a multi-user organization.
- Approval policy uses stable capability categories with `allow`, `ask`, or `deny`. MVP defaults allow worktree read/write, local Git operations, sandboxed commands, and package/source network access within platform policy; ask for additional network destinations, destructive workspace actions, setup-configuration changes, remote Git writes, and draft PR/MR publication. Host access, infrastructure credentials, metadata services, host Docker access, raw provider credentials, production secrets, and deployment are platform-denied and cannot be overridden. Initial interactive decisions are allow-once or deny; persistent project policy changes are separate explicit actions.
- Approval decisions are scoped to an actor, capability, action, run, and relevant content version; expired, duplicate, revoked, or stale approvals cannot execute new actions.
- Revocation blocks new use, terminates affected runs where required, and removes temporary credential material. Record metadata-only audit events.

### Verification

Release requires real GitHub and GitLab test repositories and actual API-key runs on each initial provider. Demonstrate remote coding, tests, browser reconnect, follow-up, draft PR/MR publication, cancellation, approval routing, crash reconciliation, duplicate delivery prevention, and credential revocation. Include negative tenant-access and sandbox-escape-boundary tests. Do not label tests successful merely because an agent says they passed: preserve command, exit status, and bounded output.

### CLI

No MuniClaw CLI is required for the MVP. Operators use inspectable service logs and documented worker operations; customers use the separate console.

## Decisions and open questions

### Confirmed with the user

- Private MVP, designed for multiple users later.
- One active user membership per organization in the MVP, using a multi-user-ready membership and actor model.
- MuniClaw is authoritative for organizations and membership; Minicloud receives scoped service identity and ownership linkage for infrastructure operations.
- Dedicated Minicloud-managed VPS per organization.
- Workspace provisioning is an explicit asynchronous onboarding action.
- GitHub and GitLab in the first version.
- Provider-specific Git publication identity is acceptable; remote task-branch divergence requires reconciliation.
- Separate console from `cloud.muni.dev`; `ai.muni.dev` is the candidate hostname.
- Existing coding harness; OpenCode is the initial candidate.
- SSE with cursor replay for browser events and outbound HTTP long-polling with leases/fencing for worker dispatch.
- Personal provider credentials in the MVP with organization scope supported by the data model and deferred from the UI.
- Messaging and native mobile follow later.

### Proposed defaults for this draft

- OpenCode first, one active task per organization, GitHub.com/GitLab.com initially.
- Shared hosted user identity with explicit MuniClaw allowlisting; independent repository with dashboard/API/core/worker modules.
- Review-triggered draft PR/MR publication; previews deferred.
- Seven-day workspace retention and 30-day event retention.

### Qualification decisions

- Pin OpenCode release/image digest and verify distribution/license obligations.
- Validate provider proxy and cancellation/recovery behavior; choose sandbox enforcement compatible with the target VPS kernel.
- Confirm VPS size from measured repository setup/build workloads, not a guessed minimum.
- Confirm shared identity integration, final name/hostname, distribution license, and retention defaults before implementation locks their public contracts.
