## Goal

Enable organization administrators to register shared model provider credentials (e.g., OpenAI, Anthropic, DeepSeek) that organization members can select when dispatching coding tasks, without each member needing an individual personal key. Administrators enforce usage guardrails including allowed model families, monthly budget caps, and membership role restrictions.

## Current patterns learned

- MVP `ProviderCredentialReference` has `CredentialScope.Personal` with `UserId` ownership.
- `ProviderCredentialService` handles validation, OpenBao secret path resolution (`municlaw/{orgId}/credentials/{credId}`), and revocation.
- `TaskLifecycleService.CreateTaskAsync` validates credential presence and scope.
- Console UI `ConnectionsModule` and `CredentialKeyEntry` manage personal keys with write-only inputs.

## Scope and non-goals

### In scope

- `CredentialScope.Organization` supporting organization-wide sharing.
- Administrator-only creation, policy configuration, and revocation of organization credentials.
- Access policy configuration:
  - Allowed model IDs or prefixes (e.g., `["claude-3-5-sonnet", "gpt-4o"]`, or `["*"]`).
  - Budget / spend limits (monthly spend cap in USD).
  - Spend tracking accumulated from task completion token usage.
  - Role restrictions (Admin-only vs all Members).
- Task creation integration: members can select available organization credentials if authorized by policy and within budget.
- Negative tests verifying policy enforcement: budget overflow rejection, unauthorized model rejection, non-admin configuration rejection.

### Out of scope

- Direct billing/credit card charging by MuniClaw (BYOK model keys only).
- Per-token rate-limiting algorithms (governed by upstream provider limits).
- Fine-grained per-user project allocation trees (reserved for future enterprise tiers).

## Requirements

### User experience requirements

- In Console > Connections, administrators see an "Organization Keys" tab alongside "Personal Keys".
- Administrators can configure a new shared credential with:
  - Provider (OpenAI, Anthropic, DeepSeek).
  - Key Name / Label (e.g., "Company Anthropic - Tier 4").
  - Allowed Models (selection or comma-separated list).
  - Monthly Spend Cap ($ USD, or unlimited).
  - Access Level (All Members or Admins Only).
- Live spend progress bar showing current spend vs monthly cap.
- When creating a task, members see a dropdown selector showing their personal keys and all accessible organization shared keys. If a model is chosen that is forbidden by an organization key, helpful validation prevents dispatch.

### Runtime and backend requirements

- `ProviderCredentialReference` extended with:
  - `Scope`: `Personal` or `Organization`.
  - `Policy`: `OrganizationCredentialPolicy` containing `AllowedModels`, `MonthlySpendLimitUsd`, `CurrentSpendUsd`, `AdminOnly`.
- Authorization check: creating/updating/deleting an organization credential requires `OrganizationRole.Admin`.
- Task dispatch check:
  - Verifies user has access to the credential.
  - Verifies requested model matches `AllowedModels`.
  - Verifies `CurrentSpendUsd < MonthlySpendLimitUsd` (if limit configured).
- Task completion / event processing updates `CurrentSpendUsd` based on reported provider usage.

### Security

- Raw API keys remain strictly write-only, stored in OpenBao/mock vault, and never emitted in API responses, SSE streams, or UI state.
- Secret path for org keys: `municlaw/{orgId}/org-credentials/{credId}`.
- Revocation of an organization credential cascades to abort any currently executing task runs actively using that credential.

### Verification

- Unit & integration tests in `MuniClaw.Tests`:
  - Org credential creation restricted to Admins (reject Members).
  - Model restriction validation (reject disallowed model).
  - Budget cap validation (reject task creation when spend >= cap).
  - Member access policy (reject regular Member when AdminOnly is true).
  - Spend accumulation on task completion.
- Console UI build and test passing.

## Decisions locked

- Personal credentials remain available and take precedence if the user chooses their own key.
- Spend tracking is advisory/enforced at task submission time using reported usage estimates. Upstream provider billing remains authoritative.
